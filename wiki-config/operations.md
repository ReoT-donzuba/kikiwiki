# 聞き書きWiki（KikiWiki）運用ルール

**このファイルは個人運用を前提にしています。** 複数人で1つのWikiを育てる場合のルール（オーナーの決め方、レビューの回し方、匿名化・昇格の承認フロー）は含めていません。チームで使う段階になったら、そのとき設計してください。

## 会話駆動での作成方針
- 会話で得た事実を優先し、推測は明示的に区別する
- ノート化の手順は `wiki-config/conversation-workflow.md` に従う
- 会話時の入力テンプレートは `wiki-config/chat-prompts.md` を利用する

## 週次ワークフロー
1. 障害対応、修正作業、繰り返し業務から新規ノートを追加する
2. `draft` を読み返し、検証が済んでいるものを `verified` へ昇格する
3. 古くなったノートは必要に応じて `deprecated` に変更する
4. 重複ノートは統合し、正本（canonical）を残す

毎週きっちりやる必要はありません。**ノートを追加するときについでに1〜2件見る**程度で回ります。

## ファイル操作時の安全チェック（Windows環境）
複数ファイルの編集や大規模な置換を行う場合、以下を必須実施する。

1. **変更前の確認**
   - `git status` で変更対象を確認する
   - `git diff` で予期しない差分がないことを確認する

2. **Encoding の明示**
   - PowerShell スクリプトでは常に `-Encoding UTF8` を指定する
   - Get-Content / Set-Content / Out-File すべてで Encoding を明示する

3. **変更後のチェック**
   - `git status` で新規差分を確認する
   - `git diff` で期待値と一致することを確認する
   - 日本語を含むファイルを読み込み、目視で文字化けを確認する
     ```powershell
     Get-Content -Path "notes/index.md" -Encoding UTF8 -TotalCount 20
     ```

4. **代替手段の優先順位**
   - テキスト置換: apply_patch を第一選択（Encoding 安全）
   - 複数ファイル操作: VS Code UI または ファイルシステム ツール を優先
   - スクリプト実行: 最後の手段（Encoding 明示 + 前後チェック必須）

## 品質ゲート
以下を満たす場合のみ `verified` とする:
- 手順を他者が再現できる
- 検証セクションが完了している
- タグが `wiki-config/tags.md` に準拠している
- 必要に応じてリスクとロールバックが記載されている

「他者が再現できる」は、**半年後の自分**を他者だと思って判断すれば十分です。

## うまく回っているかの判断
指標を測る必要はありません。次の1点だけ見てください。

- **探したいノウハウに、1回の質問で辿り着けるか。**

辿り着けなかったら、そのノートのタイトル・タグ・見出しを直します。溜め込むこと自体が目的ではないので、引けない状態が続くなら書き方を変えるサインです。

## Wikiの改善サイクル
Wikiは「作って終わり」ではなく、運用しながら継続的に改善する。

```
Schema更新（新しい気づきをテンプレ・ルールに反映）
    ↓
ノートを蓄積する（新フォーマットで自然に積み上がる）
    ↓
Lintで乖離を検出（旧フォーマットのノートが浮き上がる）
    ↓
バックフィル（Lintついでに旧ノートを更新）
    ↓
また気づきが生まれてSchema更新へ
```

### 改善フェーズの目安
| ノート数 | 推奨アクション |
|---|---|
| 10件 | 横断的知見セクションのバックフィル、Lintでスキーマ乖離確認 |
| 30件 | ディレクトリ分割を検討、タグ体系の見直し |
| 月1回 | Lint実行、Schemaと実態の乖離を修正 |

### 基本原則
- Schemaファイル（TEMPLATE.md・ai-agent-rules.md）は常に「現在の最善」を反映する
- 過去のノートはLintが収束させる。人間が全件見直す必要はない
- テンプレや運用ルールの改善もLLMに提案させてよい
